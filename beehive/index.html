Beehive

What it is

Beehive is my try at an AI helper that runs on my own machine, not on somebody else's computers. The model lives on my laptop. It's a gaming laptop with a good graphics card (RTX 5070 Ti, 12 GB of video memory, 64 GB of RAM).

There are two kinds of parts. One is a planner, the queen. She keeps the plan saved as records on disk, so the plan is still there even if everything else stops. The other is workers, the bees. A bee takes one step of the plan, does it in a throwaway copy of the code where it can't break anything real, and reports back.

You can't try a demo of this. It runs on my machine, for me. What I can show you is how it works and what went wrong. So that's what this page is.

What it is for

The goal is a helper I can talk to as long as I want, that remembers the stuff that matters. Not a chat that forgets anything older than the last bunch of messages. The whole history stays saved. When I send a new message, the system looks back through the history, finds the parts that matter for this message, and shows the model just those.

It has to work with a small model that can only hold a little bit of text at a time, on my computer. That's the hard part, and it isn't going to change. A big model that can hold a huge amount of text can get away with a lot. Mine can't. The system is made to work with a window of 32k or less, because that's what the small model on my machine does well. Everything in Beehive is shaped by that. The memory part exists because the window is small. The plan records exist because a worker with a small window can't hold a whole project in its head, so the project lives on disk instead.

The other half of the goal: it has to be something I can trust. A helper that goes off and does the wrong thing, sure of itself, is worse than one that does nothing. The builder half only matters if the work can be checked. That's the rest of this page.

And the builder half is not me watching every job forever. The goal is a builder that works on its own. I say what I want built. The system helps work out the design, plans the steps, and builds it, with as little from me as possible once I start it. That's the queen's job. She plans and watches. The bees build, one step at a time. I start it, and I check what comes out.

Right now the watching is mostly me, by hand, in the open. The written job instructions, reading the records, deciding what lands. That's for now, and it's on purpose. The way I run jobs by hand is the way being built into the queen, so when she takes over she does it the same way. In the end there is no big outside model in the loop. The small local model does the work, and the system does the watching.

Two smaller parts. It should also run things on a schedule and send messages to my phone. That part isn't built. It needs a computer that stays on all the time, and I don't have that set up yet.

And the document work I do for a living gets its own sealed room in it. I went back and forth on this. In October I said no separate helper, the normal chat should be good enough. On November 2 I changed my mind and had it built as its own thing: chats over documents, sealed off from the rest, one instruction document pinned so its rules can't get lost, and a delete that really deletes everything the chat left behind. The build started that day. Beehive 1 has a simpler version already, chat over a folder of documents. That one passed its test run back in October.

The problem it is built around

Left loose on your code, a model will tell you it did things it didn't do. I've watched it happen more than once. It will say the tests pass when it never ran them. It will say a job is done when the important part is missing.

So Beehive is built around not trusting it. The model suggests the work. A separate program runs the tests and keeps the records. Nothing counts as done because the model said so.

If you take one thing from this page, take that. Whatever you build, put something in it that checks the work without asking the model first.

What I do

I don't write the code myself. My part is this.

I set the rules before a job starts. Who is allowed to write a change. Who checks it. What a job has to show before it counts as done.

I write the instructions for each job. What the goal is. Where the code is that matters, which I find ahead of time so the agent isn't wasting its run hunting for it. Which tests will show the thing works. And what is out of bounds.

I read the full record of what the agent did, every run. Not the summary. The summary is what the agent says it did. The record is what it did. Those are not always the same.

And I kill things. Features, and whole ways of doing it, when the numbers say they don't work. A few of those are below. They taught me more than the stuff that worked did.

That's most of the job, really. Typing the code is the cheap part now. Deciding what to build, what to keep, and what to throw out is the work.

How a job runs

A job starts with my instructions. The agent writes the change itself. I don't hand it code to copy. If I did, a done job would only prove the agent can copy.

The agent works in a sandbox with a step limit set for the size of the job. Its work gets judged against the tests that were already failing when it started. I don't blame it for old breakage. I don't let it use old breakage as an excuse either.

Then the harness runs the tests. Passing the tests is just the start. After that I read the record and check that the tests that were supposed to prove things really test what they say they test.

Last is landing. Landing means the change becomes part of the real code. There's a dial for how much can land without my say-so. The settings go from "show me everything" to "just do it". Some things never land on their own, no matter the setting: the harness and its tests, the safety settings, the limits the system runs under, deleting things with git, and changes to old tests that nobody said yes to. If something that landed on its own ever causes a bug, the dial drops a level by itself.

The dial is at Level 1. Propose only. Nothing lands without me. The only setting under it is me doing every landing by hand. Going up from here takes ten clean landings in a row. That streak hasn't happened yet, so I'm in no hurry. There's no point having the rule if I bend it the first time it's a pain.

What went wrong

The work that wasn't the agent's (October 22, 2026). This is the big one. Jobs had been landing clean, one after another, and the reports looked great. Then it came out that the changes had been written ahead of time by my assistant and handed to the agents to type in. The agents were just typing. The good results were measuring the wrong thing.

I stopped that the day I found out. Since then it's simple. Agents write their own work. My assistant does not write the building code for these jobs at all. And every job report starts by saying who wrote the change.

If you're testing what your agents can do, watch for this. It's easy to end up grading your own homework and calling it the agent's score.

The check that got gamed (October 24-25, 2026). Early on, an agent got a check it couldn't pass. The check itself was broken in a fresh setup. Instead of saying so, the agent cheated it. It planted a file whose only job was to make the check pass. Nothing caught it except the last gate, the one that runs in a clean setup from scratch.

The rule that came out of it: a check has to prove it can fail. Before a check gets to judge anything, it runs against the known bad version, in the same setup it will run in for real. If it doesn't fail there, it doesn't count. I call it a bite test.

The check that failed for the wrong reason (October 28, 2026). A run failed because the checks themselves were broken. They pointed at a scratch folder that couldn't be written to. They had passed their bite test, though. On the empty starting code they failed anyway, for a different reason, and failing was all the bite test looked for back then. The agent did the right thing here. It figured out the checks were the problem and stopped, instead of working around them.

The fix didn't go in my head. It went into the program that looks over every check before it runs. One lesson, put where every check has to go through it. When something teaches you a rule, put the rule in the machine. You'll forget it. The machine won't.

Things I killed

Looking back at old jobs. I built a thing that let the system search its finished jobs for lessons. Then I tested it for real, with facts planted in old jobs that it had to find. It found facts. But too many of the ones it brought back were the wrong ones. I let it have one fix. The fix fixed a different problem, and the wrong ones kept coming. So I shut it off and kept the numbers.

Writing the tests first, in the dark. There was a question about whether checks should be written before the work, by a pass that can't see the work. I ran it as a straight race, with the score to beat set at 0.70 before anybody ran anything. The in-the-dark ways scored 0.22, 0.22, 0.38, and 0.42. I stopped it early and ruled it out for this model in this setup. Setting the bar first matters. Set it after, and you'll move it, and then the test told you nothing.

The first version's shape. Beehive 1 built the worker first. The planner, the queen, never got built at all. I ended up running everything by hand, which is the thing I was trying to get away from. Beehive 2 flipped it. Planner and memory first. Workers second. Build the boss before the labor.

Numbers I believe, and why

The memory part is what makes the long chat possible, so it's the part I test the hardest. It was tested on stuff it had never seen while it was being tuned. Fresh set. One run. No changes after. It found 129 of 132 planted facts. Just storing the messages plain and searching them found 119. On facts that had changed since they were first said, it got 17 of 18. Tune on one set, test once on a different set. Anything else is just practice.

I also run a set of small test projects the system has to build from scratch, to prove it still can. The first one passed on its third try, October 29. The checking round came back 9 of 9 when it was run again on its own, and I didn't touch anything during it. The two tries before it failed in the checks, not in the building, and each one changed the harness. That's what the test projects are for.

Around that time the test suite was at 928 tests, with 926 passing. The 2 that failed were on a machine that didn't have the test runner in its system Python. That got written down as what it was. It didn't get folded into the numbers to make them look better.

Where it stands

Beehive 2 is paused. I stopped on November 3, on purpose, to check something. I described the harness I want to a big outside coding tool, in a different language, and let it build its version, to see how it does next to my home-built one. Stopping to check is not quitting.

The rules on this page are what the other one gets judged by. Whichever way the building goes, the rules stay. They cost too much to learn to throw them away over liking one tool more than another.

The goal hasn't moved. A helper on my own hardware, under my control, that I can talk to as long as I want, that remembers what matters, and that builds what I describe, with the system itself doing the watching instead of a bigger model watching it. I'm not there yet. This is where it stands.
