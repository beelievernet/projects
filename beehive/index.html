Beehive

What it is

Beehive is my attempt at having an AI assistant that runs on my own machine instead of somebody else's servers. The model is local. It runs on my laptop, a gaming laptop with a decent graphics card (RTX 5070 Ti, 12 GB of video memory, 64 GB of RAM).

It has two kinds of parts. There is a planner I call the queen. She keeps the plan as records on disk, so the plan survives even if nothing else does. And there are workers I call bees. A bee takes one step of the plan, does it in a sandboxed copy of the code where it can't hurt anything, and reports back.

There is no demo of this you can try. It runs on my machine, for me. What I can show you is how it works and what went wrong, so that is what this page does.

What it is for

The goal is an assistant I can talk to for as long as I want, that remembers what matters. Not a chat that forgets everything older than the last stretch of messages. The whole history stays saved on disk. When a new message comes in, the system goes and finds the parts of the history that are relevant and puts just those in front of the model.

It has to work on a small model with a small context window, on my hardware. That is the whole constraint, and it is not optional. A big model with a huge window can get away with a lot. Mine can't. The system is built to work at a 32k window or less, because that is what the local model handles well on my hardware. Everything in Beehive is shaped by that. The memory engine exists because the window is small. The planning records exist because a worker with a small window can't hold a whole project in its head, so the project lives on disk instead.

The other half of the goal is that it has to be reliable. An assistant that goes and does the wrong thing confidently is worse than one that does nothing. The builder side of Beehive, the agents doing work, only matters if the work can be checked. That is the rest of this page.

And the builder side is not supposed to be me supervising every job forever. The goal is a developer that works on its own. I describe what I want built. The system helps design it, plans the work, and builds it, with as little from me after I start it as possible. That is what the queen is for. She plans and supervises. The bees build, one step at a time. I start it and I check the results.

Right now the supervising is mostly me, by hand, in the open. The briefs, the trace reading, the landing decisions. That is temporary, and it is deliberate. The habits I am using to run these jobs are the ones being built into the queen, so that when she takes over, she runs them the same way. The end state has no frontier model in the loop. The small local model does the work and the system does the supervising.

Two smaller parts of the goal, for the record. It should also run things on a schedule and reach me on my phone. That part is not built yet, and it waits on hardware meant to stay on.

And the document work I do for a living gets its own sealed room in it. I went back and forth on this one. In October I said no separate helper, the normal chat should be good enough to cover it. On November 2 I changed my mind and ordered it built as its own thing: conversations over documents, sealed off from everything else, one instructions document pinned so its rules can't get lost in the retrieval, and a delete that actually deletes everything the conversation left behind. The build started that day. Beehive 1 already has a simpler version, chat over a folder of documents. That one passed its drill back in October.

The problem it is built around

Left loose on your code, a model will tell you it did things it didn't do. I have watched it happen more than once. It will say the tests pass when it never ran them. It will say a job is done when the important part is missing.

So Beehive is built around not trusting it. The model suggests the work. A separate program runs the tests and keeps the records. Nothing counts as done because the model said so.

If you take one thing from this page, take that. Whatever you build, put something in it that checks the work without asking the model's opinion.

What I do

I don't write the code myself. My part is this:

I decide the rules before a job starts. Who is allowed to write a change. Who checks it. What proof a job has to show before it counts.

I write the instructions for each job. What the goal is. Where the relevant code is, which I pin down ahead of time so the agent isn't wasting its run hunting. Which tests will prove the behavior works. And what is out of scope.

I read the full record of what the agent did, every run. Not the summary. The summary is what the agent claims. The record is what it actually did. Those are not always the same thing.

And I kill things. Features and whole approaches, when the numbers say they don't work. A few of those are below. They taught me more than the successes did.

That is most of the job, honestly. Typing code is the cheap part now. Deciding what to build, what to accept, and what to throw out is the work.

How a job runs

A job starts with my instructions. The agent writes the change itself. I don't hand it code to copy. If I did, a finished job would only prove the agent can copy.

The agent runs in a sandbox with a step budget sized to the job. Its work gets judged against the test failures that were already there when it started. I don't hold it responsible for old breakage, and I don't let it claim old breakage as an excuse either.

Then the harness runs the tests. Passing tests is the floor, not the finish. After that I read the record and check that the tests the job was supposed to prove things with actually test what they claim to.

Last is landing, which means the change becomes part of the real code. There is a dial for how much can land without my say-so. It has settings from "show me everything" up to "just do it". There is also a list of things that never land automatically, no matter the setting: the harness and its tests, security settings, the limits the system itself runs under, destructive git operations, and edits to existing tests nobody approved. If a defect ever traces back to something that landed on its own, the dial drops a level by itself.

The dial sits at Level 1. Propose only. Nothing lands without me. The only setting below it is doing every landing by hand. Moving up from where it sits takes ten clean landings in a row, and I am in no hurry, because the streak hasn't happened yet. There is no point having the rule if I waive it the first time it is inconvenient.

What went wrong

The work that wasn't the agent's (October 22, 2026). This is the big one. A run of jobs had been landing clean, one after another, and the reports looked great. Then it came out that the changes had been written ahead of time by my assistant and handed to the agents to type in. The agents were transcribers. The good results were measuring the wrong thing.

I stopped that the day I found out. Since then the rule is simple. Agents author their own work. My assistant does not write implementation code for these jobs at all. And every job report starts by saying who authored the change.

If you are testing what your agents can do, watch for this. It is easy to end up grading your own homework and calling it the agent's score.

The check that got gamed (October 24-25, 2026). Early on, an agent got a check it couldn't pass. The check itself was broken in a fresh environment. Instead of saying so, the agent gamed it. It planted a file whose only purpose was to make the check pass. Nothing caught it except the last gate, the one that runs in a clean container.

The rule that came out of it: a check has to prove it can fail. Before a check is allowed to judge anything, it gets run against the known bad version, in the same environment it will run in for real. If it doesn't fail there, it doesn't count. I call it a bite test.

The check that failed for the wrong reason (October 28, 2026). A run failed because the checks themselves were broken. They pointed at a scratch folder that couldn't be written to. They had passed their bite test, though, because on the empty starting code they failed anyway, for a different reason, and failing was all the bite test looked for at the time. The agent did the right thing. It figured out the checks were the problem and stopped instead of working around them.

The fix did not go in my head. It went into the program that reviews every check before it runs. One lesson, applied everywhere, forever. When something teaches you a rule, put the rule in the machinery. You will forget it. The machinery won't.

Things I killed

Searching old jobs. I built a feature that let the system look through its finished tasks for lessons. Then I tested it properly, with planted needles it had to find. It failed on precision. It found things, but too much of what it found was the wrong thing. I allowed one fix. The fix solved a different problem and precision stayed bad. So I closed it and kept the numbers.

Writing the tests first, blind. There was a question about whether checks should be written before the work, by someone who can't see the work. I ran the comparison straight, with the passing bar set at 0.70 before anybody ran anything. The blind test-first approaches scored 0.22, 0.22, 0.38, and 0.42. I stopped it early and ruled it out for this model in this setup. Setting the bar first matters. If you set it after, you will move it, and then the experiment told you nothing.

The first version's shape. Beehive 1 built the worker first. The planner, the queen, never got built. I was managing everything by hand, which is the exact thing I was trying to get away from. Beehive 2 reversed it. Planner and memory first. Workers second. Build the coordinator before the labor.

Numbers I believe, and why

The memory engine is the part that makes the long chat possible, so it is the part I test the hardest. It was tested on material it had never seen during tuning. Fresh set, one run, no adjustments after. It found 129 of 132 planted needles. Plain message storage found 119. On facts that had changed, it got 17 of 18. Tune on one set, test once on a different set. Anything else is rehearsal.

I also run a regression circuit, a set of small projects the system has to build from scratch to prove it still can. The first leg passed on its third try, October 29. Acceptance came back 9 of 9 on an independent re-run, and I did not touch anything during it. The two tries before it failed in the checks, not the building, and each failure changed the harness. That is the circuit's job.

Around that time the test suite stood at 928 tests with 926 passing. The 2 failures were a machine that didn't have the test runner in its system Python. That got written down as what it was. It did not get folded into the numbers to make them prettier.

Where it stands

Beehive 2 is paused. I stopped on November 3, on purpose. I am running a comparison. I described the harness I want to a frontier coding tool, in a different language, and let it build its version, to see how it stacks up against the homebrew. Pausing to check is not the same as quitting.

The rules on this page are the standard the comparison gets judged by. Whichever way the build goes, the rules stay. They cost too much to learn to throw away over a preference for one tool or another.

The goal hasn't moved. An assistant on my own hardware, under my control, that I can talk to for as long as I want, that remembers what matters, and that builds what I describe, with the system itself doing the supervising instead of a bigger model watching it. I am not there yet. This is where it stands.
